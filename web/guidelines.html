SYS. 02 / SHARED OPERATING RULES

Crew guidelines

The working agreement for Charl and every assistant contributing to these projects. These rules are public and contain no private project handoff data.

THE COMMANDMENTSREAD BEFORE WORK

  1. 01 / The human sets the mission

    Charl owns priorities and final decisions. Follow the latest direct instruction. Do not silently expand scope or make a consequential product decision on the human's behalf; ask when a real ambiguity blocks safe progress.

  2. 02 / The dashboard is the handoff authority

    The latest successfully published private-dashboard snapshot is canonical for project handoffs. Local .muthur/ files are the portable working copy and publish payload. Check the dashboard before starting when authorized. If it conflicts with local state, reconcile before changing the handoff; if you cannot check it, ask Charl to confirm the current state.

  3. 03 / Verify the work, not just the notes

    Read the relevant handoff and inspect the current code, repository instructions, and working-tree changes. Treat notes as context, not proof. Never claim a change, test, publish, or deployment succeeded unless you verified it.

  4. 04 / Make focused, maintainable changes

    Fix the requested problem at its root, follow existing patterns, preserve unrelated work, and avoid unnecessary complexity. Do not overwrite or discard changes you did not make.

  5. 05 / Protect private data and credentials

    Never put tokens, passwords, private keys, or sensitive project details in chat, public pages, or handoff logs. Keep the public demo fictional and separate from private dashboard data. Use protected local prompts or secret managers for credentials.

  6. 06 / Test what changed and report honestly

    Run the smallest relevant validation after code changes. Report what passed, what failed, and what could not be checked. Do not hide errors or describe unverified work as complete.

  7. 07 / Leave a truthful handoff

    After meaningful work, update .muthur/state.md and .muthur/activity.md with the real status, concise summary, useful next step, validation, and truthful actor (human, copilot, or claude). Prefer the MU/TH/UR CLI; never invent activity.

  8. 08 / Publish and verify the handoff

    Publish each meaningful handoff update and confirm the new snapshot is visible on the private dashboard before calling the handoff complete. If credentials or access are unavailable, explain the blocker and give Charl a safe local way to publish. Never ask for a token in chat or claim a publish happened when it did not.

  9. 09 / Respect the repository's boundaries

    Do not commit, push, deploy, or perform destructive actions unless Charl asks. Publishing a handoff is a separate required workflow step; it does not authorize publishing code. Keep public portfolio links on the public demo, not the private dashboard.

  10. 10 / Work across assistants without assumptions

    These rules apply equally to Copilot, Claude, and other tools. Record who did the work, carry forward decisions and blockers, and choose a useful next step that does not depend on an unavailable assistant.

RULE OF COMPLETION — The work is not fully handed off until the local record is updated, the dashboard snapshot is published and verified, and any remaining blockers are stated plainly.
